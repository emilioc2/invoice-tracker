# Eternity Invoicing — Requirements Document

## Overview

Eternity Invoicing is a multi-tenant web application that allows businesses to manage clients and invoices, track payment status through a defined workflow, and automatically trigger notifications when invoices become overdue.

## Tech & infrastructure decisions

| Area | Decision |
|---|---|
| Backend | C# / .NET Core Web API, layered/clean architecture (Domain / Application / Infrastructure / API) |
| Auth | ASP.NET Core Identity (password hashing, lockout, email-confirmation/reset token plumbing) underneath, issuing JWT bearer tokens for the SPA to call the API cross-origin. Includes self-service "forgot password" flow (Identity reset token + email via `IEmailSender` + reset-password page). Also includes a separate **forced password-change flow** for temp-password logins (see "Forced password change for temp-password logins" below) — distinct from the self-service flow above, since it happens mid-session with a known current password rather than via a reset token; tracked via a `MustChangePassword` flag on the user's identity (see "Multi-business membership" below) (response-body/DB state, not a JWT claim), consistent with this row's minimal-JWT, no-refresh-token design. No refresh-token flow — an expired JWT simply forces re-login (the frontend intercepts `401` and redirects to `/login`). This stateless, no-refresh-token design also means there is no token-revocation mechanism: deactivating a user (see User entity below) transitions them to `UserStatus.Deactivated` immediately and blocks all future logins, but does not revoke any JWT already issued to that user — a token issued before deactivation remains valid and usable until it naturally expires at the end of its configured lifetime. This is an accepted limitation of the design, not a bug. |
| Database | PostgreSQL |
| Messaging | Kafka, **KRaft mode** (no separate Zookeeper container — lighter footprint) |
| Frontend | React + TypeScript |
| Email | Resend, behind a generic `IEmailSender` interface (Application layer) so the concrete provider is a one-class swap later. `IEmailSender.SendAsync` accepts an optional list of attachments (filename + bytes + content-type) alongside the plain-text body, used by the invoice Send/Resend flow below to deliver the invoice PDF. **Known limitation to document:** this implementation uses Resend's shared default sender address (no domain/DNS verification), which in sandbox mode can only deliver to the email address that owns the Resend account rather than to arbitrary third-party recipients — this is for testing purposes, so it proves the outbound integration (including attachment delivery) fires correctly on events, rather than guaranteeing delivery to each client's actual inbox. |
| PDF export | QuestPDF for generating an invoice PDF on demand. (Its free Community license has company-size/revenue eligibility conditions — acceptable here as a personal project, called out for completeness alongside the other licensing/cost trade-offs in this table.) |
| Frontend hosting | Vercel (live), using Vercel's own git integration for frontend CI/CD |
| Backend/DB/Kafka hosting | Single AWS EC2 **t3.micro**, running the full `docker-compose` stack (API + Postgres + Kafka) live. 1GB RAM is tight for this combination — mitigations: KRaft mode Kafka, trimmed JVM heap settings, lightweight Postgres config, swap file configured on the instance. |
| CI | GitHub Actions: `dotnet build`/`test` on PR, build + push Docker image to GitHub Container Registry |
| Kubernetes | Deployment/Service/ConfigMap/Secret manifests written as artifacts demonstrating container orchestration, runnable against `kind`/`minikube` — not deployed to a live cluster |

## Domain model

- **Business** — the tenant. `Id, Name, Email, PaymentDetails`. `PaymentDetails` is a nullable free-text field holding the business's default payment instructions (e.g. bank account details, a payment link) shown to clients on invoices unless overridden per-invoice — see "Business payment details" below. A single business may now have more than one person holding a membership in it, and a single person's identity may hold memberships in more than one business — see "Multi-business membership" below.
- **User identity** (credential store, via ASP.NET Core Identity) — `Id, Email (globally unique), PasswordHash, MustChangePassword`. One identity row per real-world person, regardless of how many businesses they belong to — `Email` is globally unique at this layer (enforced by Identity's `NormalizedUserName` unique index, since username = email here), which is what makes one email usable across multiple business memberships instead of colliding on a second registration. `MustChangePassword` lives here, not on the membership below, because a temp password is a property of the one credential an identity has — not of any particular business membership — see "Multi-business membership" for the full reasoning.
- **UserBusinessMembership** — `Id, UserId (the identity above), BusinessId, Role (Owner | Staff), Status, StatusChangedAt`. No `Email` field of its own — `Email` lives solely on the identity (see above) and is unique there; anything needing to display a membership's email (e.g. the Users list) joins via `UserId`, rather than carrying a second copy that could drift. One row per (person, business) pair — this is what used to be modeled as a single 1:1 `User` row before multi-business membership was introduced (see "Multi-business membership" below for the full model, the migration from the old shape, and why `Role`/`Status` live here rather than on the identity). `Status` is a `UserStatus` enum (`Active | Deactivated`), changed only via the guarded `UserBusinessMembership.TransitionTo(UserStatus)` domain method (see `architecture.md`'s "Domain invariants: centralized status transitions"); it defaults to `Active`. An Owner can transition a Staff membership in their own business to `Deactivated`, which blocks logins *for that business* immediately (a deactivated membership in Business A has no effect on the same identity's membership in Business B, if any) — but, per the Auth row above, does not revoke a JWT already scoped to that business and issued before the change; it remains valid until it expires. This transition is reversible: an Owner can later transition a `Deactivated` Staff membership in their business back to `Active` (reactivation). `StatusChangedAt` is set by `TransitionTo` on every transition. An Owner can never deactivate their own membership — see Permissions below. **Note:** the `Owner` role is displayed to end users in the UI as "Admin" (a display-only label change, unaffected by this restructuring) — the internal role identifier and the persisted `"Owner"` string are unchanged.
- **Client** — the business's customer being invoiced. `Id, BusinessId, Name, Email, Phone, Address, CreatedAtDate, LastModifiedDate, Status, StatusChangedAt`. `Status` is a `ClientStatus` enum (`Active | Removed`), changed only via the guarded `Client.TransitionTo(ClientStatus)` domain method (see `architecture.md`'s "Domain invariants: centralized status transitions"); it defaults to `Active`. The only legal transition is `Active → Removed` (user-facing "Remove") — there is no reverse transition; a removed client cannot currently be restored. `StatusChangedAt` (non-nullable `DateTime`) is set by `TransitionTo` on every transition and records when the client's status last changed, replacing the former nullable `ArchivedAt` timestamp — kept separate from `LastModifiedDate`, which bumps on any field edit, not specifically a status change.
- **Invoice** — `Id, BusinessId, ClientId, InvoiceNumber, CreatedAtDate, IssueDate (nullable), DueDate, Status, Subtotal, TaxRate, TaxAmount, Total, Notes, PaymentDetails, LastModifiedDate, ArchivedAt`. `InvoiceNumber` is auto-incrementing *per business* (e.g. `INV-0001`, `INV-0002`, each business starts its own sequence) — needs a per-business counter generated transactionally: a `BusinessInvoiceCounter` row (one per business) incremented under row-level locking within the same transaction as invoice creation, to avoid race conditions when multiple Staff users create invoices concurrently. (A native Postgres sequence per business was considered and rejected: it would mean dynamically running `CREATE SEQUENCE` on every business registration, which doesn't fit a system where tenants are created at runtime.) Tax is calculated at the invoice level (single `TaxRate`/`TaxAmount` against the subtotal), not per line item. `ArchivedAt` follows the same nullable-timestamp pattern as Client. `CreatedAtDate` is set at row creation (while still `Draft`) for audit purposes. `IssueDate` is `null` while `Draft` and is never directly editable by the business — it's set automatically, and becomes immutable, the moment the invoice is sent (`Draft → Unpaid`); `DueDate` remains editable like other fields only while still `Draft`, per the existing edit-lock rule. `PaymentDetails` is nullable free-text, mirroring `Business.PaymentDetails`: when an invoice is created, it is populated from the business's *current* `PaymentDetails` value at that moment, unless the caller explicitly supplies an override at creation time; once set, it does not retroactively track later changes to the business's default — the same "fixed once set" treatment the system already applies to other invoice state (e.g. `IssueDate` once sent). Like other invoice content, it remains editable only while the invoice is still `Draft`, per the existing edit-lock rule — once sent, it is locked along with line items/due date/client. When populated (whether from the snapshot or an explicit override) it appears on the invoice PDF and in the Send/Resend and overdue-reminder email bodies (see "Invoice email delivery" below); when null/empty, nothing renders for it anywhere.
- **InvoiceLineItem** — `Id, InvoiceId, Description, Quantity, UnitPrice, LineTotal`
- **Notification** — record of an email-based notification sent to a client: an overdue reminder (automatic, via the Kafka pipeline) or an invoice-sent/resent copy (manual, via Send/Resend — see "Invoice email delivery" below). `Id, InvoiceId, NotificationType (OverdueReminder | InvoiceSent), Status (Pending | Sent | Failed), SentAt (nullable), Channel, Message, SourceEventId`. `SourceEventId` (unique) ties the notification back to what triggered it: the Kafka event's `eventId` for an `OverdueReminder`, or a freshly generated `Guid` per attempt for an `InvoiceSent` row (Send and Resend each generate their own `SourceEventId` — there is no Kafka event on this path). The row is inserted as `Pending` *before* the send is attempted, not after, in both cases — so a crash between sending and recording never results in the same event being processed twice, and (for the Send/Resend path) never silently loses the fact that an attempt was made. See `architecture.md`'s consumer design and "Invoice email delivery" section for the full sequences.

### Status workflow
`Draft → Unpaid` (manual, business finalizes/sends — this is also the moment `IssueDate` is set) → `Unpaid → Overdue` (automatic, background job once `DueDate` passes unpaid) → `Unpaid/Overdue → Paid` (manual) → `Draft/Unpaid → Cancelled` (manual; not allowed once Paid).

### Permissions
Role is now a property of a `UserBusinessMembership`, not of a person's identity — the same identity can be Owner of one business and Staff of another, each independently.
- **Owner**: full CRUD on clients/invoices in that business + can create, deactivate, and reactivate other memberships for that business. Exactly one Owner membership exists per business (the person who registered it, or who later used "Add a business" — see "Multi-business membership" below) — a business's Owner membership cannot be duplicated, and **an Owner can never deactivate their own membership in that business**, so a given business can never end up with no one able to manage its users. This invariant is per-business: it does not restrict how many *different* businesses the same identity may be Owner of at once.
- **Staff**: full CRUD on clients/invoices in that business, no user management. This includes the Users screen itself — the frontend hides the Users nav tab and page from Staff entirely, though `GET /api/users` remains callable by any authenticated user at the API layer (unchanged). Deactivating a Staff membership only affects that person's access to that one business — any other membership they hold elsewhere is untouched.

### Multi-user onboarding
First registration creates the Business + its Owner user. Owner adds Staff users directly from the UI (email + auto-generated temp password, emailed via the `IEmailSender` abstraction) — no separate invite-token flow.

## Forced password change for temp-password logins

A Staff user created via the Multi-user onboarding flow above receives an auto-generated temp password by email. Logging in with a temp password must not grant normal access to the system until the user has set their own password — this is standard security practice for temp-password flows, so a password nobody but the business chose (and that passed through an email) isn't left as the account's permanent credential.

- The identity's `MustChangePassword` flag is set `true` at the moment a Staff user's temp password is created (alongside the existing temp-password email), and cleared to `false` only on that user's next successful password change via the flow described here.
- On login, the API reports `MustChangePassword` back to the caller alongside the existing login response; the SPA must redirect to a forced change-password screen and block navigation to anything else in the app until the change succeeds — the user keeps the JWT already issued (it remains valid and usable to perform the change) but cannot reach clients, invoices, or any other screen while the flag is still `true`.
- The forced change happens **mid-session, with the user's current (temp) password known to them** — this is a different situation from "I forgot my password entirely," which the existing self-service forgot-password/reset-password flow (reset token via email) already covers. The two flows are independent and neither replaces the other: forgot-password/reset-password is unaffected by this feature.
- Completing the forced change requires only a new password meeting the same password-strength rules as every other password set in the system — the user does not need to re-supply their current (temp) password, since already holding a valid JWT issued at the moment they logged in with it is proof enough; on success, `MustChangePassword` clears to `false` and the user has normal access from then on, with no new login required.
- This flow applies only to Staff users created with a temp password. A newly-registered Owner chooses their own password at registration, so `MustChangePassword` is always `false` for a freshly registered Owner.

## Multi-business membership

One person's email identity can belong to more than one business — as Owner of one and Staff of another, or Staff of several, or Owner of several. This replaces the earlier 1:1 assumption (one `User` row = one business), under which registering a second business with an email already in use anywhere would fail outright at the credential-store layer.

**Identity vs. membership:** a person's login credential (email + password + `MustChangePassword`) is one thing, globally unique; which business(es) they belong to, and what role they hold in each, is modeled separately as a `UserBusinessMembership` row per (person, business) pair. See the Domain model above for the full shape.

**Registering a new business:**
- `POST /api/auth/register` (unauthenticated) creates a brand-new identity + a new business + an Owner membership, exactly as before, **only when the submitted email has no existing identity**. If the email already belongs to an existing identity, registration is rejected (`409 Conflict`) — the response directs the caller to log in and use "Add a business" instead, rather than silently reusing or colliding with the existing account.
- An **already logged-in** identity can register an additional business via a separate action ("Add a business"), which creates the new business plus a new Owner membership for the caller's existing identity — no new identity or password is created — and immediately switches the caller's active session into the new business (see "Switching business" below).
- The same existing-identity question applies to Owner-created Staff invites: if the invited email already has an identity, a new Staff membership is attached to that existing identity (no new temp password generated, and no new identity created) rather than failing or duplicating the account; the invited person is notified by email to log in with their existing password. If the invited email has no identity yet, the Staff invite behaves exactly as before (temp password, `MustChangePassword = true`).

**Logging in with multiple memberships:** `POST /api/auth/login` still takes `{ email, password }`. If the credentials match an identity with exactly one `Active` membership, login behaves exactly as it always has — this is, and must remain, the common case with zero visible change. If the identity has credentials matching but **zero** active memberships, login fails identically to a bad password (no information is leaked about which part failed). If the identity has **more than one** active membership, login does not issue a usable access token on this call; instead it returns a short-lived, single-purpose token and the list of businesses/roles the identity can choose from, and the caller must complete the login via `POST /api/auth/select-business` with the chosen business — see `architecture.md`'s Auth routes for the exact shapes. A membership that is `Deactivated` never appears as a selectable option and can never be logged into, even if other memberships for the same identity are active.

**Switching business:** once logged in, a person whose identity holds more than one active membership can switch their active session to a different one of their own businesses via an explicit "switch business" action, without re-entering their password. The server always re-validates that the caller's identity actually holds an active membership in the requested business before issuing a new token scoped to it — a client can never switch into a business it doesn't belong to by supplying an arbitrary business id. Switching issues a brand-new JWT scoped to the new business/role; the previous token is not revoked and remains usable until it naturally expires, consistent with this system's existing no-refresh-token, no-revocation design (see the Auth row above).

**Permissions remain per-business:** the "exactly one Owner per business" rule, and "an Owner can never deactivate their own account," are unaffected by multi-business membership — both are evaluated per business, not per identity. The same identity being Owner of two businesses does not create a second Owner of either individual business, and does not let that identity deactivate its own membership in either one.

## Business payment details

Businesses can maintain a default payment note — bank account details, a payment link, or other payment instructions — so clients know how to pay. This is the business's first dedicated settings/profile concept; no such screen or field existed before it.

- **Who can edit it:** any authenticated member of the business — Owner or Staff — can view and edit `Business.PaymentDetails`. This is a deliberate exception to the otherwise Owner-gated pattern for business-wide settings (e.g. user management, which is Owner-only — see Permissions below): payment details are treated as everyday business information rather than an administrative control, so no role restriction applies.
- **Where it lives:** a new settings screen, reachable by all authenticated users of the business (not role-filtered, unlike the Users screen), lets a user view the business's current `PaymentDetails` and save changes to it.
- **Effect on invoices:** see `Invoice.PaymentDetails` in the Domain model above, and "Invoice email delivery" below, for how the business-level default flows onto individual invoices (snapshot at creation, overridable) and from there to what the client sees.

## Invoice email delivery

Sending an invoice (`Draft → Unpaid`) emails the client a copy of the invoice — the PDF as an attachment, plus the invoice's details (invoice number, amount, due date) in the email body — using the same `IEmailSender` abstraction as the rest of the system. When the invoice's `PaymentDetails` is set (whether snapshotted from the business default or explicitly overridden — see the Domain model above), the email body also includes a payment-details line alongside the other invoice details, so the client can see how to pay without needing to open the attached PDF; when `PaymentDetails` is null/empty, the line is omitted entirely from both the email body and the PDF. The status transition itself always succeeds on its own merits; email delivery is attempted as a best-effort side effect and never blocks or reverses the transition. The outcome of each attempt (`Sent` or `Failed`) is recorded as its own `Notification` row (`NotificationType = InvoiceSent`) and reported back to the caller separately from the transition result, so the UI can distinguish "sent successfully" from "sent, but email delivery failed."

Because email delivery isn't guaranteed, a business can **resend** the same invoice email at any time after it has first been sent — for an invoice in `Unpaid`, `Overdue`, `Paid`, or `Cancelled` status (any status other than `Draft`), resending is just "send the client another copy of this invoice," independent of payment status. A resend does not transition the invoice's status and does not reactivate the Draft-only edit lock — it only re-delivers the same PDF+details email and records another `Notification` row (fresh `SourceEventId`, same `NotificationType = InvoiceSent`).

**Accepted limitation:** unlike the Kafka-driven overdue-reminder path, nothing automatically retries a `Pending` `Notification` row left behind by a process crash mid-send on this path — there is no event to redeliver. A human notices (e.g. a `Failed` or stuck `Pending` row in the Notifications list) and resends manually.

**Overdue reminder email content:** the automatic, Kafka-driven overdue reminder (`NotificationType = OverdueReminder`) is structured the same way as the Send/Resend invoice email above — a greeting, the invoice's amount due and due date, and a closing line — with the invoice PDF attached, instead of a single bare status sentence with no attachment. The wording differs because the framing differs (a reminder that payment is late, not "here's a copy of your invoice"), but a client reading either email should recognize them as the same kind of correspondence from the same business. For the same reason, when the invoice's `PaymentDetails` is set, the overdue reminder's body also includes the payment-details line, not just the attached PDF — treating the body text inconsistently with the Send/Resend email (payment details in the PDF but silently missing from the reminder's own text) would undercut the "same kind of correspondence" goal this section already states; when `PaymentDetails` is null/empty, the line is omitted here too, same as Send/Resend. The Kafka event itself stays lightweight (invoice/client summary fields only, no line items) — the consumer sources the PDF and the full invoice detail itself from the database, the same way the Send/Resend handlers do. See `architecture.md`'s `OverdueNotificationConsumer` section for the exact sequence and template.

## In scope

- Business + Owner registration/login; Owner-created, Owner-deactivated, and Owner-reactivated Staff memberships (an Owner can never deactivate their own membership in that business); JWT auth, scoped to one active business per token; a business-selector screen at login when one identity's credentials match more than one active membership, and an explicit switch-business action afterward — see "Multi-business membership"; self-service forgot-password/reset flow; forced password-change flow for temp-password logins (distinct from the self-service flow, mid-session with a known current password)
- Client CRUD (soft-delete via `ClientStatus.Removed`, not hard delete)
- Invoice CRUD with line items (archive via `ArchivedAt`, not hard delete), full status workflow above
- Kafka-driven overdue pipeline: background job flags overdue invoices → publishes event → consumer sends a structured reminder email (letter format, PDF attached) via Resend + persists a `Notification`
- Invoice email delivery on Send (PDF attachment + invoice details in body), with a manual Resend capability for any invoice past `Draft`; delivery outcome (`Sent`/`Failed`) tracked per attempt via `Notification` records and reported separately from the Send/Resend action's own (always-independent) success
- Business-wide default payment details (`Business.PaymentDetails`), viewable/editable by any authenticated business member (Owner or Staff) via a new settings screen; a per-invoice `PaymentDetails` override, snapshotted from the business's current default at invoice creation (or set explicitly), editable only while the invoice is `Draft`, and shown to the client on the invoice PDF and in the Send/Resend/overdue-reminder email bodies when present
- Notifications list view
- Invoice list with filtering (status, client, date range) + dashboard summary (outstanding total, overdue count, etc.)
- Responsive mobile support — a single breakpoint (~768px): below it, a collapsible hamburger/drawer navigation replaces the desktop header nav, and list views (Clients/Invoices/Users/Notifications) render as cards instead of tables; forms and dialogs get touch-target sizing (44×44px minimum). Tablet-width screens inherit the unchanged desktop layout — no dedicated intermediate tablet treatment.
- PDF export of an invoice
- Swagger/OpenAPI docs
- Full `docker-compose` stack (API, Postgres, Kafka in KRaft mode) — this is both the local dev environment and what's deployed live to the EC2 instance
- Live deployment: frontend on Vercel, backend stack on the AWS EC2 instance
- Kubernetes manifests as artifacts (not live)
- GitHub Actions CI for backend; Vercel's own pipeline for frontend
- Automated tests: backend unit tests (status transitions, overdue calculation, totals), backend integration tests (API against a real Postgres), a handful of frontend component tests
- README: run/build/test instructions, architecture overview, and a design decisions & trade-offs section (Resend sandbox-mode delivery limitation, AWS t3.micro RAM trade-off, why K8s manifests aren't live, etc.)

## Out of scope

- Real payment gateway integration (`Paid` is a manual status flip)
- Recurring invoices / invoice templates
- Multi-currency, i18n
- Actual live Kubernetes cluster deployment (manifests only)
- Advanced reporting/analytics beyond the basic dashboard summary
